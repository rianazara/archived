## Quiz

1. Name the serving-side technique where a cheap model drafts tokens and
   the expensive one verifies them in parallel — then say how it differs
   from continuous batching and from KV caching. _(model internals,
   inference and cost)_

2. In the layered defence for a RAG system over internal documents, which
   layer is ranked most important, and why does it have to sit before
   everything else? Name at least three of the other layers. _(AI
   security)_

3. Why does in-memory session state work at ten users and fail at ten
   million? Give the four architectural moves that fix it. _(agents and
   orchestration)_

## Connection

`securing-rag-systems` ranks **injection protection** — keeping retrieved
content structurally separate from system instructions — as a defence
layer, and `scaling-stateful-agents` ranks **session isolation** the same
way. Both are the same principle at different boundaries: content from
elsewhere must never be able to act as instruction, and one user's context
must never be able to reach another's.

## Answers

**1. Speculative decoding.** A cheap draft model proposes tokens and the
expensive model verifies them in parallel, so you pay full price only for
verification rather than for generating every token sequentially.

The three are solving different problems:
- **Speculative decoding** reduces the cost of producing *one* response.
- **Continuous batching** keeps the GPU busy *across* requests, admitting
  new ones as others finish instead of waiting for a whole batch — a
  throughput and utilisation technique.
- **KV caching** reuses attention state across the tokens of a single
  generation rather than recomputing it at each step.

So: one makes a response cheaper, one makes the fleet busier, one stops
redundant recomputation within a response.
_(`entries/ai/llm-inference-optimizations.md`)_

**2. Policy-aware retrieval is ranked first.** Access control is applied
*before* retrieval, filtering by role, department, permission and data
classification, so the model can never retrieve a document the user isn't
authorised to see. It sits first because **everything downstream is weaker
than it** — once an unauthorised document is in the context window, every
later layer is trying to prevent a leak that has already partly happened.

The other layers:
- **Output filtering / DLP** — a pass after generation catching
  credentials, API keys, salaries, internal project names and roadmap
  detail before they leave.
- **Prompt hardening** — system prompts forbidding disclosure or following
  instructions found in content; a useful layer, insufficient alone.
- **Injection protection** — sanitise retrieved documents, keep retrieved
  content structurally separate from system instructions, ignore
  instructions embedded in documents.
- **Logging and auditing** — queries, retrieved documents and responses,
  so incidents can be investigated.
- **Red teaming** — regular testing for injection, jailbreaks, leakage and
  unauthorised retrieval.
_(`entries/ai/securing-rag-systems.md`)_

**3. It fails because you cannot scale horizontally when every instance
holds different state.** Load balancing becomes guesswork, and a crashed
pod takes its live sessions with it — so adding capacity makes things
worse rather than better. It is a cliff, not a gradual decline.

The four moves:
1. **Externalize all state** — session state to a fast shared store,
   long-term memory to a durable one, so any worker can serve any request
   because state is fetched rather than remembered.
2. **Isolate every session** — scoped namespaces, and separate execution
   environments for sensitive workloads, so one user's context can never
   reach another's. (Note: cross-session leakage is a confidentiality bug,
   not a performance one.)
3. **Make workers stateless and disposable** — spawn, do the job, shut
   down, with no reliance on warm instances holding anything.
4. **Make long tasks asynchronous** — queue the work, return a job ID
   immediately, notify by polling or webhook, rather than blocking a worker
   for a 30-second tool call.

What this is really testing: not "use Kubernetes", which is an answer about
tooling, but stateless workers, externalized state, session isolation,
async execution and context lifecycle management — answers about
properties.
_(`entries/study/scaling-stateful-agents.md`)_
